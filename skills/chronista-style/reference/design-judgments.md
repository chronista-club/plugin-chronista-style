# 設計の判断集 — 気づく問いと、直し続ける作法

> 最初から完璧なコードを目指さない。未来は予想できない。
> 開発中に「ここはこう整理した方がいい」と気づけること、そしてその改善を続けられることの方が大事。

この文書は、設計時に守る規則の一覧ではない。**開発中にこう感じたら、こう問う**という気づきの問いと、**気づいたものをどう直し続けるか**の作法を、Chronista の実例と一緒に置く。実例は実リポジトリの design docs（「やってはいけない」節）、レビュー記録、リファクタの履歴から引いている。

三つの軸は `chronista-style` ルートの「設計哲学」のとおり — **責務**（変わる理由ごとに置く）、**Simplicity**（副作用と計算の分離。原典: [Grokking Simplicity](https://www.manning.com/books/grokking-simplicity) — Eric Normand）、**Straightforward**（一本の経路、導出、十分で止まる）。

---

## 第一部 — 気づきの問い

### 責務 — 変わる理由ごとに置く

コードをどう並べるかより先に、**誰が何を持つか**。責務が散らばると、一つの変更が多くの場所を触り、似た実装が増え、一つのファイルが何役も兼ね、並列開発が渋滞する。

| こう感じたら | こう問う |
|---|---|
| この記述、ここにあるべき？ | **この記述が変わるとき、何が変わったからか。** その変わる元のそばに置く |
| 似た実装が複数ある | **片方のバグは、もう片方でもバグか。** 然りなら同じ責務で一箇所に。否なら偶然の類似で、3 行の重複のまま置く |
| 変更が方々に波及する、並列作業がぶつかる | **この変更は何箇所を触るか。** 多くの場所を触るなら責務が散らばっている。直すのは大きなマージではなく、責務を一箇所に戻すこと |
| ファイルが巨大で見通しが悪い | **このファイルを開く理由は何通りあるか。** 行数が減っても、開く理由が減らなければ見通しは戻らない |
| ライブラリに機能を足したくなった | **それは consumer の領分ではないか。** 選択の自由を奪う依存や UI は consumer に残す |

**実例**

- **同じ概念の二つの顔を、変える層に分けて置く** — VP の「ディレクトリはどの層の責務か」。結論は「Project には持たせない、持たせたら負け」。logical root（単一・デバイス非依存）は Lane が持ち、resolved cwd（具体・デバイス依存・drift する）は Pane / Session が持つ。一つの概念を一箇所に置くのではなく、変わる理由が違う顔を別の層に置いた（VP domain-model、2026-05）
- **形が似ていても責務が違えば共通化しない** — vpcode の transcript 保存。`log_file_in` / `append_in` / `read_all_in` は総称化して流用したが、`truncate_if_needed_in` は流用しなかった。「正本は切らない。肥大対策は rotation でなく、古い session file ごと削除する別層」。同時に、書き手を配信流路に乗せなかったことで競合が「構造的に消えた」（vpcode、2026-08）
- **兼務は、計算を抜いた後に残る** — Ladyland の `RotoService.swift`。ページ座標、LCD 表示、14bit 値、短い MIDI 入力の分類、SysEx の分類、差分投影の 6 つを純粋層に抜き、`Roto/` に 16 ファイルと 12 本のテストが生まれた（1,944 → 1,677 行）。それでも RotoService は送信・受信・影・admin port・起動の複数の理由で開かれるファイルのまま。計算の抽出は責務分割の前処理であって終点ではない（bikeboy-ladyland PR #141、2026-09）
- **土台は直列、末端は並列** — auth・スキーマ・共有 package の変更は渋滞するので main lane で一本の線に流し、UI や独立タスクは並列にする。技術的理由（共通基盤の一貫性）と並んで、監督する人の帯域も判断軸（mako、2026-08-30）
- **consumer の領分に踏み込まない** — creo-ui に auth 関連 prop・Auth0 SDK 依存・login UI を出さない（identity）。font picker や web-hosted font asset を入れない（typography）。「fork でなく override。fork は upstream drift の元」
- **下の層に上の層の都合を書かない** — 特定 app の pane kind や Rail を primitive に hardcode しない（layout-engine LE-12、principal-layout PL-3）。2D の consumer に 3D Frame protocol への依存を持ち込まない（PL-1）

### Simplicity — 副作用と計算の分離

コードは三つに分かれる。**data**（事実。不変）、**calculations**（入力から出力への純粋な変換。いつ何度呼んでも同じ）、**actions**（外界と相互作用する。いつ・何回呼ぶかが意味を持つ）。Action の中に埋まった計算は、テストできず、再利用できず、責務の線も引けない。

| こう感じたら | こう問う |
|---|---|
| このロジック、テストで直接叩けない | **Action の中に計算が埋まっていないか。** 抜いて純粋関数にし、Action は薄い接着剤にする |
| 同じ入力なのに結果が変わる | **時計・乱数・環境を中から読んでいないか。** 引数で渡す。時間は常に外から |
| 事実と解釈が混ざっている | **記録しているのは事実か、解釈か。** 事実は log に残し、解釈は別の層で導出する |
| 共有状態を複数の経路が触る | **タイムラインを描いたか。** 読み → 書きの間に別の経路が割り込めるなら壊れる。共有を減らすか直列化する |
| 元のデータが壊れた | **変更でなくコピーを返しているか。** 信頼境界の外から来たものは入口でコピーする |

**実例**

- **時間は常に外** — layout-engine「時間駆動を interpolate に内蔵しない。t は常に外、driver が進める」（LE-7）。補間は t を受け取る純粋関数で、進めるのは外の driver
- **事実は log、解釈は別層** — layout-engine「蒸留アルゴリズムを engine に実装しない。事実は log、解釈は CC」（LE-17）
- **純粋層の抽出** — Ladyland の 6 commit。それぞれ「X を純粋層へ分離」+ テスト 1 本の粒度。抽出前に `docs/roto-control/refactor-invariants.md` へ実測と制約を書き出し、「担当: `RotoPageLayout`」と責務を明記した
- **Action はイベントで、細く** — lane-reconcile「reconcile を定期 tick で全 lane を全読みにしない。intent が変わるのは動詞のときだけ。tick は『読めなかった』を『0 件』と誤認する窓を増やす」。「write lock を握ったまま spawn しない。spawn は隔離してから insert」（VP design 53）
- **空集合の Action** — GFP の CreateSession で案件内 PDF が 0 枚だと `all()` が真になり、何も検証せずに pin されていた。空のときに Action を発火させるかは明示的に決める（gfp-estimate L-3 レビュー、2026-09-03）
- **信頼境界で防御的に** — 検証キャッシュの stamp を size + mtime から (size, mtime ns, ctime ns, inode) へ。mtime は `touch` で戻せる。ctime はユーザー空間から戻せず、rename は inode が変わる。root で ctime まで偽装する相手は信頼境界の内側（同上）

### Straightforward — 一本の経路、導出、十分で止まる

入力から出力までが一本の線で追えること。同じ事実を二箇所に持たないこと。要らないものを足さないこと。Grokking Simplicity は抽象化を勧める側に立つが、Chronista はそこに「十分で止まる」を対置する。

| こう感じたら | こう問う |
|---|---|
| 同じ事実が二箇所にある | **正本はどれか。** 残りは導出する。状態フラグは持たず射影する |
| 値を変換してまた戻している | **表現を往復させていないか。** 元の表現を直接使う |
| 名前を見ても場所や役割が分からない | **名前は経路を語っているか。** 位置を持たない語（sidebar / nav）を API に出さない |
| 将来のために広げたくなった | **次の consumer はもう現れたか。** 現れてから広げる。3 行の重複は早すぎる抽象化より良い |
| 統一のために構造を足したくなった | **空なら描かなくてよいか。** 揃えるために空の構造を敷かない |
| 「最速」「最新」を理由に選びたくなった | **target spec で十分か。** 十分なら選ばない |

**実例**

- **導出できるものは持たない** — layout-engine「離散状態フラグ（focused / minimized / maximized）を再導入しない。全て場の射影・導出」（LE-3 / LE-20）。「サイズを構造・記法に書かない。二重 SSOT の再発」（LE-4）
- **供給路は一本** — lane-reconcile「client に pane 一覧と session 一覧を両方配らない。供給路 2 本の再生産」「`console_mode` を表示用だからと残さない。中間の投影を残すと必ずまた乖離する」（VP design 53）。principal-layout「Rail 選択に route 以外の signal を作らない。route が唯一の SSOT」（PL-4）
- **表現を往復させない** — vision-cross-platform「Apple Vision の matrix output を `matrixToEuler` で再変換しない。`face.pitch/yaw/roll` を直接使う」
- **Schema を分裂させない** — 「Frame schema を Immersive 専用に fork しない。解釈拡張で対応」（immersive-field）。「Schema を platform ごとに分裂させない」（vision-cross-platform）
- **名前は経路を語る** — principal-layout「sidebar・nav 等、位置を持たない語を API・class・data-attribute に出さない」（PL-2）
- **次の consumer が来てから広げる** — layout-engine「VP 以外の consumer 要件の先取りをしない。2nd consumer が現れた時に protocol を広げる」
- **空なら描かない** — VP design 50「額縁の統一を『全 pane に同じ帯を敷く』と解しない。空なら描かない」
- **十分で止まる** — vision-cross-platform「『最速』を理由に Phase B を選ばない。target spec で WebView は十分」（CV-6）
- **重複メソッドの統合** — 統合後の抽象が自然なら強く美しくなる（やる）。統合のために不自然な抽象を発明するなら、3 行の重複の方がまだ直線的（やらない）。ルールではなく、この問いで個別に判定する

## 第二部 — 気づいたときの作法

気づきは開発中に来る。それを捨てず、かつ今の作業を壊さずに、改善を続ける。

- **手は止めない。** 依頼の範囲内なら、小さく分けて commit する。Ladyland の粒度 — 一つの commit で純粋層を一つ抜き、テストを一本付ける。完璧な形を先に決めず、抜けるところから抜く
- **範囲外なら直さず `/spark`。** 気づきは火花として原文のまま pack し、最終報告で触れる。GO の範囲の外を直すと、レビューする人が「何の変更か」を見失う。Fable は近くのコードを直したがるので、この一行が要る
- **抜く前に、設計意図を一本のテストで pin する。** 「内容 sha をキーにするから案件をまたいで共有される」のような意図は、テストが無いと将来の変更で黙って壊れる（GFP PR #90 レビュー）。抜いた後も同じ振る舞いだと言える根拠を先に作る
- **実測と制約は文書に戻す。** 「担当: X」で責務を明記し、実測の日付と裁定を積み、「コードのコメントには制約を短く残し、経緯をここに置く」（`refactor-invariants.md` の形）。踏んだ地雷は design の「やってはいけない」に追記する（`spec-design-guide`）
- **土台の整理は直列で。** 責務の置き直しは渋滞の根を触る作業なので、main lane で一本の線に流す。末端は並列でよい（`parallel-dev`）
- **基準は「次に触るときに前より見通しが良い」。** 今回で全部を直さない。開く理由が一つ減った、正本が一つになった、テストで叩けるようになった — どれか一つで前進

## 言語での表現

| 概念 | Rust | Ruby |
|------|------|------|
| data | `struct` / `enum`（`#[derive(Clone)]`）。所有権が共有可変を防ぐ | `Data.define` / frozen な `Struct`、`freeze` した Hash |
| calculations | 純粋な `fn`（`&mut` なし、I/O なし）。`&self` は読み取り専用 | `self` の状態を触らないメソッド、`module_function` |
| actions | `async fn`、`&mut` を取る `fn`、I/O | I/O、`!` 付きの破壊的メソッド、外部 API 呼び出し |
| コピーして返す | `.clone()` + 変更 + return | `dup` / `with`（`Data`）+ 変更 + return |
| 信頼境界でのコピー | API 境界での `.clone()` / `.into()` | 入口で `dup.freeze`、`JSON.parse` 直後に整形 |
| 層の下向き | モジュール階層、`pub` / `pub(crate)` | 名前空間、`private_constant` |

Rust の所有権は、共有可変状態をコンパイル時に潰す。`&mut` の排他は Timeline の問題の多くを型で解く。Ruby にはその強制が無いので、`freeze` と「calculations は `self` を触らない」を自分で守る。
